# UI chassis qualification and takeover synthesis

## 1. 裁决

选择：**以现有 exact baseline 为唯一 T0，在 Campaign branch 上一次性直移完整 runnable dependency
closure；随后按 typed Product ingress、真实 `Agent | Chat`、isolated Pi Native Host 的顺序换脑，并在
首个 production candidate 前删除旧 Engine 权威和 buildable donor mirror。**

这不是 whole-tree adoption，也不是 component cherry-pick：

- 行为保全以 Web + Desktop + Service + contracts/shared + build closure 为物理单位；
- production acceptance 以 rights、identity、唯一事实权威和 normal/failure/recovery proof 为单位；
- T1 物理接管只是可回退的 non-candidate checkpoint；最早到 T4 的真实 Chat 与 folder-backed Agent
  vertical slice 通过后，才存在 production candidate。

Stage 1 尚未完成，F-03 必须保持 `open`；但后续维护者校准已经关闭 authorized icon corpus 的工程分叉：
4,014 files 全量保留并获准在 source/artifact 中适配和再分发，禁止 used-only pruning。F-03 仍需最终
artifact、notice/SBOM 与同 SHA 独立验证，不能从本研究直接提升。

## 2. 证据如何汇合

| Evidence | 结论 | 对施工的约束 |
| --- | --- | --- |
| rights / lineage | fixed code tree、MIT notice、original-upstream 连续历史和 legal copy 相互一致；完整 4,014-file corpus 后续获维护者授权；40 个 donor graphics、brand copy/screenshots 未获 clearance | T1 全量保留 corpus 并做 line/fill path、Glyph API、fixed/source/artifact integrity；former product graphics 全部替换，最终 artifact 生成 SBOM/notices |
| source-domain audit | Web 拥有母体与恢复/性能机制，也直接理解 donor Thread/Provider；Desktop 成熟但只监督一个混合 backend；Server 同时拥有 Product control 与 Engine Session/queue/retry/Package authority | Web-only 不可运行，Server-whole 不可接受；必须直移 dependency closure 后按 Product UI / Desktop Host / Product Service / Native Host 重切 |
| takeover slice | exact baseline 已存在，复制整树没有新证据；逐组件迁移会产生 `apps -> vendor` 长期依赖和薄 replacement state | T1 直移、T2 identity + typed ingress、T3 `Agent | Chat`、T4 Native Host + old-authority deletion；每个 checkpoint 可回退但不得提前升级 claim |

## 3. 被否决的路线

### 原样整树成为生产根

否决原因不是“代码太多”，而是它会同时提升 donor identity、未 clearance 资产、Provider-first ontology、
static model mirror、single-backend topology 和旧 Engine authority。它只可作为短暂非候选机械 checkpoint，
不能拥有 production status。

### 只搬 Web 或挑优质组件

否决原因是母体的恢复/性能/Workbench 行为跨 root route、store、contracts、Service 和 Desktop。只挑
视觉文件会丢 subscription lease、cursor/resnapshot、stream buffer、scroll anchoring、xterm lifecycle、
packaged static paths 和 crash recovery，并被迫让 root production code 长期依赖 `vendor/ui`。

### 把现有 Server 直接改名 Product Service

否决原因是 `provider`、`orchestration`、`agentGateway` 与 persistence composition 实际拥有 accepted
turn queue/steer、Session、retry、runtime event、model/provider ontology 与 Package/Skill behavior。
路径改名不能改变事实权威。

### 先删除整个 Server 再重写

否决原因是 HTTP/WS admission/backpressure、projection repair、Workspace containment、Git/checkpoint、
PTY、attachment crash recovery、automation 和 diagnostics 是成熟的 Product Control / system capability
机制。把错误 aggregate 与有价值机制一起删掉会违反冰山行为保全。

## 4. 锁定的 checkpoint 边界

### T0 — exact provenance baseline（已存在）

`vendor/ui` 只作 immutable evidence。复用已记录 install/build/typecheck/macOS desktop smoke 和上游失败；
除非 revision/tree/toolchain/packaged path 等触发器变化，不重复旧 probe。

### T1 — runnable source/identity closure（non-candidate）

Git-native 迁入 Web、Desktop、Server->Service、contracts/shared、生产 build scripts/config/lock/patches 和
完整 authorized icon corpus 和实际需要资产。marketing、donor plans/audits/docs/screenshots/CI policy 不属于
runtime closure。T1 同时要求 product identity、source provenance、corpus integrity 和 root-to-vendor hard green；
仅 pre-enumerated mixed execution debt 保持 expected-red。它不得作为 release candidate。

### T2 — typed Product ingress and isolated Host boundary

- 建立 Product-owned `Workspace / Conversation / Entry / Run / EngineBinding / ResourceRef /
  OperationReceipt`；
- root route/store 只消费 typed Product facts，Pi/ACP/provider raw wire 与 generic payload 在边界终止；
- 同一真实 journey 只有一个 projection writer，临时 translator 在 acceptance 前删除。

### T3 — approved UI mother under real `Agent | Chat`

保持 shell、row grammar、Composer、Timeline、Queue、Workbench 与 panes 的批准几何，改掉 donor
Chat/Studio/Provider-first ontology。一级入口固定 Agent 左、Chat 右；区别只来自 Primary Folder 与执行
authority。完成稳定中英文案、键盘/屏幕阅读器、IME/CJK 与同状态视觉复核。

### T4 — isolated Native Host and authority deletion

Desktop 分别监督 Product Service 与 Native Host；只有 Host import Pi SDK / executable ecosystem。Product
只拥有 admission、durable Conversation/Run/receipt 和 pre-dispatch Queue；Pi 拥有 accepted operation、
Session/transcript/compaction/branch/Package private state。覆盖 reject、crash/restart、delivery-unknown no
blind replay 后，删除 donor Provider registry、accepted queue/steer/retry/session/runtime journal 和临时
compatibility path。

## 5. 第一条 production-candidate journey

同一个 frozen candidate 必须贯通：

```text
Chat / folder-backed Agent Composer
→ Product admission + durable intent
→ accepted | rejected | delivery-unknown receipt
→ supervised isolated Pi Native Host
→ Pi-native Session / model / thinking / tool stream
→ typed Product facts
→ preserved Timeline / Queue / Workbench
→ cancel, Host crash/restart and safe recovery
```

不可用的成熟域保留 truthful unavailable + re-entry，不借首个 Runtime 尚未接通删除 Git、PR、Kanban、
Automations、Viewer、Diff、Terminal、Browser、child 或 Package discovery presentation。

## 6. Design 的硬输入

1. 设计必须把 T1-T4 分成 dependency-ordered Concepts，并明确哪些 checkpoint 只是 branch rollback，
   哪个才允许 production candidate。
2. 每个 source-domain deletion 记录 old anchor、target owner、normal/failure/recovery replacement、proof；
   “已搬目录/已改名”不算接管。
3. Product Service 和 Desktop 的 dependency scan 对 Pi SDK / executable ecosystem 必须为零；Web 也不接收
   raw Engine payload。
4. Desktop health 至少拆成 window/renderer、Product Service、Native Host、Engine availability，不再用一个
   backend boolean 关闭整个 Workbench。
5. contracts 按 product facts、desktop IPC、native-host ingress、external-engine ingress、system capability
   分责，不建新的大而全 General Engine API。
6. authorized corpus 使用 complete registry 并对 fixed/source/artifact 全量 filename+byte 校验；Glyph API
   source-neutral，禁止 dynamic silent fallback、used-only pruning 或第二套 functional icon system。
7. generated route tree、theme seed、dist/sidecars/artifact 从改写后的 source 确定性生成；不得复制本机
   `node_modules`/dist/cache。
8. F-03/F-04 由独立 reviewer 基于同一 immutable candidate 决定；研究生产者不提升 Campaign。

## 7. 仍然开放但不阻塞 Design 的问题

- 最终 OmniMind brand form/palette 留给 Agent/Chat 真实表面校准；T1 temporary prior icon 不构成 palette 决策。
- Browser automation host 的最小最终位置要由 scoped capability 和 fault test 证明，不能仅凭目录决定。
- Git/checkpoint 的哪些行为落 OperationReceipt、哪些只即时查询外部事实，要在真实 journey 中裁决。
- Windows/Linux packaged path、webview、PTY 和 update evidence 要在 identity/path 改变后重新取得。
- 旧 Web storage-mock 与 attachment failures 属 baseline defect 还是接管阻碍，要在受影响 test migration 时
  诊断，不改写成“上游全绿”或提前扩大本研究。

这些问题会阻止对应 claim verified，但不构成再开同类 Explore 的理由。没有新的 material source/right/
authority 反证时，下一步直接进入 Design → QbD 1，而不是继续制造研究文档。
