# Document authority and UI-contract audit

This investigation asks one consequential question: can a fresh Agent recover the complete approved product and UI direction from the repository without reconstructing this chat?

Research mode is internal. External research is deliberately skipped because the decision concerns repository information ownership, and fixed-source product evidence has already been collected at an exact revision. Re-running external discovery without a changed source, platform or falsifier would not change the framing.

## Facts

- Repository history previously contained `architecture/` and `research/`, but the Pi-native reset deleted both while shrinking five root documents by thousands of lines.
- The compressed README retained `Agent | Chat` and the UI mother label but lost detailed Composer, Queue, Timeline, Viewer, child, structured-question, performance, CJK and accessibility contracts.
- The compressed README silently renamed Settings from the previously confirmed `Models / Agents` boundary to `Pi / Engines`.
- Fixed source at revision `6aca3dcc505894481430967c2acb762b3dd1b358` contains a large Product Server, not only a renderer, and directly uses native Pi session services in `vendor/ui/apps/server/src/provider/Layers/PiAdapter.ts`.
- The same adapter explicitly reports unsupported Host UI APIs, so native SDK use does not prove complete Package UI compatibility.
- The exact baseline installs, builds and typechecks, but upstream full tests are not green. The observed Web result was 38 failures and 3,413 passes; a legal-brand check also fails on required attribution.
- The user confirmed `Models / Agents / Packages` after being shown the competing navigation choices and their architectural consequences.

Detailed fixed-source observations and limitations are maintained in [`research/source-review.md`](../../../../research/source-review.md). The complete accepted UI contract is maintained in [`architecture/workbench.md`](../../../../architecture/workbench.md).

## Contradictions found

1. “README is the only product and architecture truth” conflicts with the need for a detailed UI contract that remains readable and maintainable.
2. “Keep only the source UI” conflicts with the source tree's mature receipts, projections, persistence, reconciliation and desktop infrastructure.
3. “Keep the entire source Runtime” conflicts with native Pi Session, queue, Tool, Package and recovery authority.
4. A visible editable Queue and Pi native queue appear duplicative until the dispatch boundary is explicit.
5. Donor identities must be absent from product ontology but present in honest research and legal evidence.

## Strongest counter-case

A single giant README reduces navigation and makes precedence obvious. The counter-case is real: split documentation can drift or become a hiding place for speculative design.

However, repository history shows the larger failure mode. Mixing constitution, architecture, research and exact-SHA evidence made the root unreadable; later compression deleted approved UI behavior. The remedy is an explicit authority graph, task routing in `AGENTS.md`, one complete UI contract, deterministic link/keyword checks and no status duplication—not returning every information lifetime to one file.

## Selected synthesis

The evidence confirms the framing:

- root README owns doctrine and adoption disclosure;
- architecture owns accepted stable contracts;
- research owns falsifiable evidence and superseded reasoning;
- execution brief owns order;
- Campaign owns status.

The Product Control Plane/native execution boundary is responsibility-based. The product Queue owns editable pre-dispatch intent; after acceptance, a Run receipt replaces that item and the Engine owns native operation semantics. This resolves the apparent duplicate queue without deleting the approved UI.

Remaining uncertainty is verification, not design: a fresh independent review must try to find a missing UI contract, competing authority, broken link or statement that could still authorize a destructive rewrite.
