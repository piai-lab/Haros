# Document authority and UI-contract preservation

This repaired PRD turns the selected synthesis in the
[document audit](research/document-audit.md) into observable repository requirements. The first
version of this PRD and its Design received an independent
[`FAIL`](qbd/design-audit.md). The human then selected the linked
[full-scope repair and scoped re-audit](decisions/qbd-1-repair.md). That `FAIL` remains the verdict
on the earlier design; this repair does not reinterpret it as approval.

This Bundle is a task artifact, not a durable product owner. Product doctrine and production
adoption remain in [`README.md`](../../../README.md). Stable contracts belong in
[`architecture/`](../../../architecture/README.md), with the complete normative UI contract in
[`architecture/workbench.md`](../../../architecture/workbench.md). The accompanying
[Design](design.md) specifies the future repository repair and its executable proof boundary. No
product, architecture, governance, source, execution or Campaign file is changed by this architect
assignment.

## Outcome

A fresh Agent, using only repository state, can:

1. identify the sole owner for doctrine/adoption, stable architecture, evidence, construction
   order, Campaign status and routing/safety;
2. recover the complete future Workbench contract, including onboarding, provenance, Models,
   Agents, Packages, policy-versus-enforcement truth, external-Engine capability/no-fallback and
   the fixed plugin/skill discovery lineage;
3. recover one durable process topology from Execution and one durable product-object definition
   from Product State without treating `AGENTS.md` or the execution brief as alternate owners;
4. distinguish an exact adopted-source provenance zone from production author structure without
   weakening exactness, rights or donor-leakage checks;
5. follow one read order and one current next action without repeating unchanged baseline probes;
6. run focused and candidate gates that can pass while the exact source baseline remains intact;
7. prove, from immutable Git objects, which paths a repair changed.

The outcome is not more parallel prose. It is one owner-and-reference graph, one complete UI owner
and one executable quality boundary.

## Users and decisions supported

- A fresh implementer deciding what to preserve, adapt, feature-gate or delete from the fixed UI
  mother.
- A maintainer changing doctrine, architecture, evidence, order or Campaign status without
  creating a second owner.
- A reviewer deciding whether a documentation/governance repair silently changed Runtime,
  Package behavior, process topology, product objects or the exact source baseline.
- A source-adoption worker proving that a declared exact subtree remains exact while donor identity
  cannot leak into production or generated surfaces outside it.

## Required authority split

Each fact class has exactly one durable owner. Other documents may route or summarize without
redefining it.

| Fact class | Sole owner | Required behavior | Must not own |
| --- | --- | --- | --- |
| Product identity, strategic doctrine, non-negotiable product boundaries and production source adoption | [`README.md`](../../../README.md) | Concise constitution; machine-readable adoption disclosure; links to topical owners | Complete UI behavior, process/file topology, research history, order or Campaign status |
| Stable responsibilities, product facts, process topology and complete UI contract | [`architecture/`](../../../architecture/README.md) | Current effective contract in the topical owner | Fixed-source observations, execution order or acceptance status |
| Fixed-source facts, falsifiers, failures and superseded reasoning | [`research/`](../../../research/README.md) | Provenance, limitations and reopen triggers | Current product contract, order or completion status |
| Construction order and stage gates | [`execution-brief.md`](../../../execution-brief.md) | Consume architecture and state what happens next | Product objects, process/file topology or new architecture decisions |
| Campaign acceptance state and evidence references | [`missions/independent-omnimind-v1.md`](../../../missions/independent-omnimind-v1.md) | Single active status matrix and evidence pointers | Detailed design, source interpretation or work plan |
| Agent routing and repository safety rules | [`AGENTS.md`](../../../AGENTS.md) | Read order, topical routing, fail-closed ambiguity and operational safety | Product constitution, UI ledger, topology, object catalog, order or Campaign facts |
| Bounded framing, requirements, design and challenge history | [this Bundle](index.md) | Explain and audit this repair through ordinary links | Durable product, architecture, execution, governance or Campaign truth |

An apparent conflict is a failed repository state. Neither read order, modified time, Campaign
status nor this Bundle decides which duplicate sentence wins: the sole owner is repaired and every
affected route/summary is reconciled in the same bounded candidate.

## Requirements

### R1 — One discoverable owner per fact

The root constitution must state the five durable content owners: doctrine/adoption, architecture,
research evidence, execution order and Campaign status. The architecture and research indexes must
route to their topical owners. `AGENTS.md` must contain only read/task routing, fail-closed working
rules and repository safety. The execution brief must contain only ordered stages, entry/stop
conditions and links to accepted contracts.

A reader must not need repository history, this Bundle, chat history or an automated summary to
discover any owner.

### R2 — One complete future UI contract

[`architecture/workbench.md`](../../../architecture/workbench.md) is the only complete normative UI
contract. The root may state product-level consequences and other architecture files may own facts
or process semantics that the UI projects. Neither may become a second UI ledger.

The implementation authorized after QbD must add every missing user-visible consequence in R4 to
Workbench itself. This PRD's inventory is an acceptance view for that future repair, not a durable
replacement. Workbench remains normal readable Markdown; headings, frontmatter and index order are
not a machine schema.

### R3 — Preserve the already approved mother surface

The future Workbench owner must continue to express all existing approved families:

- `Agent | Chat`, Agent before Chat, Projects above Groups, Agent location/write authority and
  folderless/read-only Chat with explicit `Send to Agent`;
- one Conversation renderer, Composer, Engine/Model/Thinking choice, row grammar, navigation,
  keyboard behavior and drag alternatives;
- editable pre-dispatch Queue, visible Run/receipt boundary, Timeline, Activity, structured
  Question, child Conversation, Team and dynamic Workflow behavior;
- files, search, reveal, tabs, split panes, Viewer, Diff, Changes, Terminal, generated Output, Git,
  Pull Requests, Kanban, Automations, recovery/location/trust, Browser, Source Control, Side Chat
  and Subagents;
- large/unknown/missing/corrupt/changing content, Remote delay/disconnect, stale Diff, real PTY and
  locally contained failures;
- approved geometry, density, tokens, light/dark state, motion and reduced motion;
- truthful progress, incremental projections, stream batching, bounded DOM, virtualization,
  stable scroll, background updates, bounded memory, Chinese/English, CJK/IME, keyboard and
  screen-reader paths;
- source anchor, direct transplant, behavior proof, same-state visual review, human approval for
  material visual drift, truthful unavailable states and the protected-versus-deletable gate.

Lack of first-slice wiring is never deletion authority for one of these domains.

### R4 — Complete the missing Workbench product-control surface

The future Workbench contract must add all of the following user-visible consequences without
copying Product State or Execution state machines.

| Surface | Required normal behavior | Required unavailable/failure/recovery behavior |
| --- | --- | --- |
| First-run onboarding | State that OmniMind is independent and `Powered by Pi`; identify Pi as the default bundled-native Engine; lead through a real Provider/Model connection or a supported local path; explain Agent versus Chat and where permissions become relevant | Auth cancel, expiry, missing runtime, no compatible Model and offline state preserve progress and offer a truthful retry/settings path; onboarding never claims all Packages or Engines are equivalent |
| Provenance | Engine selector shows the real Engine/source for the next Run; Package detail says that native Packages run in the Pi runtime; About, Licenses and diagnostics expose product, runtime, exact version/source and legal attribution at the appropriate detail level | Missing/unverified version or source is shown as unknown/unverified, never invented or hidden; ordinary surfaces avoid repetitive branding while source-detail surfaces remain complete |
| Models | Settings › Models owns connection, Provider, Model, Thinking/Reasoning, authentication and health presentation; choices show availability and compatibility for the next Run | Expired auth, unavailable Provider/Model and unsupported Thinking are distinct; no static product mirror silently outranks runtime facts |
| Agents | Settings › Agents distinguishes the built-in native Agent from external Agents; shows installation/source, version, capability, session/Model limits, permission truth and diagnostics | Missing protocol, offline process, unknown capability, version mismatch and unsupported operation remain explicit; the user gets a re-entry or diagnostic path, not fabricated parity |
| Packages | Settings › Packages supports Catalog/Curated/Verified discovery; source/rights/trust/exact artifact; Native/Bridged UI/PTY/Unsupported compatibility; install review; activation generation; update staging; active lease; current/LKG; rollback; License and fault presentation | Unverified is not trusted; Unsupported blocks activation with reason; install/load/update failure preserves the prior good generation; active Runs never hot-swap; Package failure does not masquerade as sandbox containment |
| Permission truth | Every material action can show user policy (`Approval required / Auto / Full access`) separately from actual enforcement (`host-enforced / engine-enforced / mixed / unverified`) | Unknown enforcement remains `unverified`; process isolation alone is never presented as filesystem/network sandboxing; denial and post-dispatch uncertainty have accurate outcomes |
| External Engine | Composer/selector shows capability differences for the next Run, including unsupported Model, Thinking, queue/control, Package, file/write or structured UI capabilities; namespaced enhancements may appear where real | An unavailable Engine/Model never silently falls back to Pi or another source; the selection and input remain recoverable, the Run is not dispatched under a different source, and unsupported capability is explained in place |

Default views stay calm and progressively disclose diagnostics. Truth may be compact; it may not be
omitted.

### R5 — Preserve and adapt the fixed plugin/skill discovery lineage

The exact baseline's `/plugins` route and `PluginLibrary` are a protected source-domain lineage,
not a permanent donor Provider ontology. The source anchors are:

- `vendor/ui/apps/web/src/routes/_chat.plugins.tsx`;
- `vendor/ui/apps/web/src/routeTree.gen.ts` for the `/plugins` registration;
- `vendor/ui/apps/web/src/components/PluginLibrary.tsx` for plugin/skill browse, search,
  capability, loading, empty and error states.

The future Workbench contract must name this lineage and map its product consequences:

- Package discovery, trust, compatibility, install/activation/update/rollback and Package-contained
  capability detail belong under Settings › Packages;
- enabled/discovered Skill presentation may surface in Package detail, Agent capability detail and
  the Composer where relevant;
- search, installed/enabled state, source failures, unsupported discovery and working-directory
  requirements remain behavior to preserve or deliberately supersede with proof;
- donor provider tabs, donor brand, `Plugin` as a generic product category and donor discovery
  APIs are replaceable implementation/ontology, not protected names.

Deletion requires source anchor, direct transplant or explicit behavior replacement, renewed proof
and the existing visual/product gate. A truthful unavailable state still preserves lineage and a
re-entry path.

### R6 — Durable topology and objects live only in architecture

[`architecture/execution.md`](../../../architecture/execution.md) must be the sole detailed owner
of the process and target responsibility topology. It must reconcile Renderer/Product UI, Desktop
Host, Product Service, isolated Native Host and External Engine boundaries, including the intended
`apps/desktop`, `apps/service` and `apps/web` responsibility split. The root and architecture index
may summarize and route; `AGENTS.md` and the execution brief may only link.

[`architecture/product-state.md`](../../../architecture/product-state.md) must be the sole product
object catalog. The existing seven objects remain the durable set. Package source/activation is a
Product responsibility, and a Package generation is a value frozen into activation/Run receipts,
not a separately mandated `PackageGeneration` aggregate. The execution brief must remove its
entity list and refer to Product State.

### R7 — Queue and execution ownership remain unambiguous

1. Product owns editable, ordered pre-dispatch intent and the next-Run choice snapshot.
2. Product admission converts that intent into a `Run` and dispatch receipt.
3. After Engine acceptance, native queue, steer, follow-up, retry, abort and settlement remain
   Engine-owned.
4. `delivery_unknown` retains visible input and prohibits blind replay; it does not silently return
   the item to the editable Queue.

Workbench owns visible behavior, Product State owns fact transition and Execution owns process
authority. Their interface statements agree without three copies of a state machine.

### R8 — Exact adopted-source zones are evidence, not author structure

An exact provenance zone is derived only from a `source-adoptions` entry that declares immutable
repository-baseline metadata for each of its `paths`. It is never inferred from the directory name
`vendor`, from `classifyPath`, or from a broad ignore rule.

For the current `ui-mother` adoption, the future disclosure and checker must bind `vendor/ui` to
repository baseline commit `2445acb987e443b44b7dc819de3de44c3d68b391` and Git tree
`630f17e61abc478114bf83c1d740977c9f68b910`. The candidate tree must match that object exactly.
The fixed subtree and legal text are not mutated to make production naming checks green.

The quality boundary must:

- validate required adoption fields, HTTPS source, exact revision, rights, mode, update policy and
  tracked legal text;
- reject missing, overlapping, nested, non-existent, modified, added or deleted declared exact
  roots;
- exempt only declared exact roots from production author-root/depth/name and donor-identity rules;
- keep configured `toolRoots` outside production author naming/structure checks, without treating
  them as adoption evidence or permitting them to declare product authority;
- reject undeclared `vendor` subtrees and scan all author paths, author text and generated output
  outside declared exact roots for donor leakage;
- retain the narrow README, `LICENSES/` and `research/` evidence exceptions;
- classify dependency/build artifacts inside an exact provenance zone explicitly as non-production
  provenance output, while scanning generated output outside the zone; non-ignored unexpected
  files inside the zone fail exactness.

### R9 — Evidence, read order and current next action are coherent

The mandatory order in `AGENTS.md`, the active Campaign and this task route is:

1. `README.md`;
2. `architecture/README.md` and every involved topical owner in full;
3. `execution-brief.md`;
4. the active Campaign, for status only;
5. `research/README.md` and relevant evidence only for provenance, prior decisions or a possible
   falsifier.

Authority does not derive from sequence. The order only prevents a fresh worker from using status
or evidence as design.

README, execution brief and Campaign must acknowledge that the exact tree comparison, install,
build, typecheck and unchanged macOS desktop smoke are already recorded in Source Review with
known limits. The current next action is to repair/freeze the architecture/UI authority, conduct
independent review of the recorded F-03/F-04 evidence and remaining rights/assets gaps, map
approved source domains, and then begin the isolated Native Host slice. The same unchanged smoke
must not be requested again absent a listed revalidation trigger.

### R10 — Deterministic checks are bounded regression alarms

A future read-only document-contract validator must fail with a stable rule and exact path when:

- a canonical owner or required local route is missing;
- owner scope or the mandatory read route disappears;
- Workbench loses an R3–R5 coverage family;
- `Agent | Chat`, Projects above Groups or `Models / Agents / Packages` is no longer affirmative;
- onboarding/provenance, Models, Agents, Packages, permission policy/enforcement, external
  no-fallback or plugin/skill lineage anchors disappear;
- the Queue admission/acceptance/no-replay boundary disappears.

It inspects bounded paths and ordinary text/links. It does not parse headings, frontmatter, index
ordering or verdict words as lifecycle/authority state. Passing proves known anchors remain, not
semantic completeness.

### R11 — Independent semantic challenge remains mandatory

Before decomposition, a fresh independent reviewer must attempt to find:

- any approved UI behavior that remains normative only outside Workbench;
- two plausible owners for the same durable fact;
- an incomplete Package, provenance, permission or external-Engine failure/recovery path;
- a plugin/skill mother domain that could still be deleted while the sentinel stays green;
- an adoption exemption broader than declared exact roots, or an exactness/leakage blind spot;
- a stale next action, inconsistent read order or acceptance criterion without an executable path;
- hidden Runtime, Package, product-object, process-topology, source or Campaign mutation.

The new audit must explicitly carry the prior `FAIL`, human repair decision, closed findings,
remaining risk and exact change. Only the human calibrates its verdict.

### R12 — Documentation freeze is not product completion

This task can prove that the future contract is complete and guarded. It does not prove that the
transplanted UI works, that each source domain is mapped, or that Campaign F-10/F-12/F-13/F-16 is
satisfied. Those require real source, behavior, failure, performance, accessibility and same-state
visual evidence at the implementation/final SHA.

## Constraints

- This architect assignment changes only Bundle PRD, Design, linked decision/interface Concepts
  when needed, and Bundle index.
- It does not edit `AGENTS.md`, product/architecture/research/execution/Campaign documents,
  governance scripts/tests, `vendor/ui`, legal text, tool configuration or product code.
- The later repair reconciles owners in place; it adds no giant alternate README, UI ledger,
  topology manifest, acceptance register, parsed Markdown schema or second Campaign.
- The complete Package/UI surface is not narrowed or deferred; unavailable is presentation state,
  not deletion authority.
- The one-owner doctrine and exact source baseline are non-negotiable.
- Existing unrelated working-tree changes belong to the user and are preserved.

## Non-goals

- Implementing the future owner/governance repair or any renderer, Control Plane, Host, Package or
  Engine code.
- Revalidating unchanged source inputs or promoting a Campaign claim.
- Defining a new product IA, changing `Models / Agents / Packages`, or reopening the accepted
  product synthesis.
- Treating text sentinels as semantic proof or workflow state.
- Creating work Concepts before the repaired Design receives a fresh independent QbD 1 audit and
  recorded human decision.

one owner per durable fact, Workbench as complete UI owner, the existing IA decisions, explicit
policy/enforcement and capability/no-fallback truth, exact declared-source preservation and
architecture-owned topology/product facts.

repaired author does not approve its own design and does not authorize implementation or
