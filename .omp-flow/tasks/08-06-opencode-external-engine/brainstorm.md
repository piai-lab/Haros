# Brainstorm: Run one real OpenCode external Engine

The observable problem is not whether OmniMind can launch another CLI. It is whether one real
external Engine can accept the next Run in the same durable Product Conversation without taking
over Product facts or being flattened into Pi's deeper native semantics.

The provisional first-principles anchor is therefore: preserve one visible Conversation and one
Product admission/receipt/recovery truth while crossing into an independently owned OpenCode
Session. The principal contradiction is that ACP exposes a real Session and streamed interaction,
but a stdio prompt request may cross the send boundary without a separate durable acceptance ACK.
OmniMind must show useful external execution while refusing to infer delivery or replay a
non-idempotent prompt after an ambiguous disconnect.

The irreducible outcome is one explicit OpenCode next-Run choice that reaches the exact real
OpenCode process, produces visible streamed/final facts and opaque Session lineage, and retains
truthful capability and permission differences. Pi remains the unchanged default. Every
unavailable or uncertain path preserves the exact user input and selection and performs zero
fallback dispatches.

The maintainer has locked OpenCode `1.14.40` and `opencode acp`; Gemini, Claude headless, Codex
app-server, PTY and thin custom bridges are not alternatives in this Bundle. Low-risk organization
inside the current Product/Service/Web owners is autonomous. OpenCode installation, update,
configuration, credential copying, bundling and redistribution are outside authority.

The strongest counter-hypothesis is that ACP `session/prompt` supplies only request completion and
stream notifications, not evidence that safely separates pre-acceptance loss from accepted but
unsettled loss. If exact protocol/source evidence and a real process probe cannot establish a
truthful boundary, the correct result is a visible unsupported/degraded checkpoint or escalation,
not a fabricated accepted receipt, PID-based inference or automatic retry.

The framing will be revised if exact OpenCode `1.14.40` evidence shows a different transport,
capability, permission or Session contract than the observed initialize response, if model/auth
selection requires Product-owned secrets or global mutation, or if the current singular Product
runtime catalog cannot be extended without inventing a generic multi-Engine ontology. The first
practice test is the linked bounded ACP research: exact bytes and source/license, initialize and
Session surface, process lifecycle, permission requests, stream/final/cancel behavior, and the
earliest externally provable delivery fact.

[Investigate the exact OpenCode ACP boundary](research/opencode-acp-boundary.md).

## Evidence-driven reframe

The first research round proved the strongest counter-hypothesis. OpenCode `1.14.40` can produce
real prompt-correlated stream facts and a final response, but its ACP v1 path supplies neither a
prompt acceptance acknowledgement nor an accepted-operation reference. A successful stdio write,
Session creation and `available_commands_update` are not prompt acceptance. The real cancel path
also has no acknowledgement and can still settle as `end_turn`.

That fact conflicts with the current sole execution owner, which requires an Engine-accepted
operation reference before Product records authority transfer. The Task's stop condition is met.
No Design or implementation is authorized from this Bundle until the owner boundary is explicitly
resolved. The bounded alternatives and recommendation are recorded in
[the Research synthesis](research/synthesis.md).
